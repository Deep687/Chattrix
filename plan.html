01

What we're building

An Internal Policy & Compliance Assistant. Think of it as each company's private "ask-HR / ask-IT" bot, where a workspace = one company:

  • A company is a workspace (your existing hub, already renamed). Employees join it.
  • Admins upload the company's policy docs — HR handbook, IT & security policy, leave & benefits, code of conduct.
  • Any employee asks in plain English — "How many casual leaves do I get?", "What's the WFH policy?"
  • The app answers from only that company's documents, cites the exact policy section, and says "I don't know based on the provided documents" when it isn't covered.
  • Each company's data is isolated in the query layer — Acme employees can never see Globex's policies, and a regression test proves it.
Why this beats the average "chat with a PDF"

The market is saturated with generic single-user PDF demos. Aiming the same engine at one real workflow — company policy Q&A — makes it read as a product, and three things make it rare (exactly what interviewers probe): (1) secure multi-tenancy — one company's policies can't leak into another's answers, proven by a test; (2) measured quality — a golden-question eval harness so you can say "recall@5 went 0.62 → 0.89 after adding a reranker"; (3) production instrumentation — per-query token cost and latency. Clones have none of these.

02

What is RAG? (in plain English)

An LLM is smart but has two limits: it doesn't know your private documents, and it can "hallucinate" (make things up). RAG — Retrieval-Augmented Generation — fixes both by feeding the model the right pieces of your documents before it answers.

The analogy: instead of asking a brilliant friend to answer from memory, you first hand them the exact three pages that contain the answer, then ask. Here's the loop:

STEP 1

Ask

User types a question in a workspace.

→
STEP 2

Retrieve

Filter to that workspace, then find its most relevant chunks.

→
STEP 3

Augment

Paste those chunks into the prompt as context.

→
STEP 4

Generate

The model answers from that context, with citations.

The clever part is Step 2. How do you find "relevant" chunks? You turn text into numbers (called embeddings) that capture meaning, then find the chunks whose numbers are "closest" to the question's numbers. The tenant filter comes first — you only ever search within the asking workspace's chunks. The glossary at the bottom explains every term.

03

What you'll learn (in order)

Learn each idea right before you build the step that needs it — not all at once. Half a day each is plenty to start.

  1. Embeddings — turning text into meaning-vectors

    The single most important concept. An embedding is a list of numbers representing a piece of text's meaning. Similar meaning → similar numbers.

    ReadGemini — Embeddings docs · Pinecone — Vector embeddings explained

  2. Chunking — splitting documents into pieces

    You can't embed a whole 40-page PDF as one blob. You split it into ~500-word "chunks" with a little overlap, and embed each chunk.

    ReadPinecone — Chunking strategies

  3. Retrieval & similarity search

    Embed the question, then compare it to every chunk using cosine similarity and keep the top few (top-K). That's "retrieval."

    ReadPinecone — What is RAG

  4. Grounded generation + the prompt contract

    Put the retrieved chunks in the prompt and enforce four rules: answer only from this context, cite the source chunk, say "I don't know based on the provided documents" when the answer is absent, and don't speculate. Prompt design is a real part of RAG, not an afterthought.

    ReadGemini — Text generation docs

  5. Laravel jobs & queues (you'll use these)

    Embedding a document takes a few seconds, so it runs in the background as a queued Job. Your queue is already configured.

    ReadLaravel — Queues

  6. (Stage 2) Hybrid search & reranking

    Combine vector similarity with keyword full-text search, then rerank the top-20 down to the best top-5 with a cross-encoder before generation. This is the single biggest quality lever after basic retrieval — and a measurable "before/after" interview story.

    ReadPinecone — Reranking

  7. (Stage 2) Evaluation — with real metrics

    What separates a tutorial from a production RAG engineer. Build a golden dataset of question → expected-answer pairs and measure retrieval (precision@k, recall@k, MRR) and generation (groundedness/faithfulness via an LLM-as-judge, answer relevance). Track scores over time so each change shows a measurable delta.

    ReadRagas — RAG evaluation

  8. (Stage 2) Observability & cost

    Log per-query token counts, an estimated provider cost, and latency broken down by stage (embed / search / rerank / generate). Remember models have context limits — retrieval quality beats quantity, and more chunks isn't better.

Swap the in-PHP cosine search for pgvector on the same Postgres, add hybrid search + a cross-encoder reranker, measure the quality delta on a golden dataset, and log per-query cost/latency. The "measured quality" story — no new language yet.

Extract embeddings + retrieval + generation into a Python FastAPI service that Laravel calls (LlamaIndex / LangGraph optional). Completes the Next.js + Laravel + Python profile — reached by evolving a shipped project, not restarting.

Why Laravel first, then Python?

The AI ecosystem is Python-first, and "Laravel + Next.js + Python for AI" is the strongest long-term profile. But you learn RAG faster in a language you already know, and shipping M1–M3 in Laravel guarantees a working demo before you add Python. Python is Stage 3 — an evolution of a live project, never a prerequisite.

06

Glossary — every term, simply

Embedding
A list of numbers that represents the meaning of a piece of text. Text with similar meaning gets similar numbers.
Vector
Just another word for that list of numbers. A text-embedding-004 embedding is a vector of 768 numbers.
Chunk
A small slice of a document (say ~500 words). You embed chunks, not whole documents, so retrieval can pinpoint the relevant part.
Cosine similarity
A math formula (0 to 1) that measures how "close in meaning" two vectors are. Higher = more similar. This is how you find relevant chunks.
Top-K
The number of most-similar chunks you keep for the answer (e.g. top 4). "K" is just that number.
Retrieval
Step 2 of RAG: embedding the question and finding the top-K closest chunks.
Grounding
Making the model answer only from the provided chunks, instead of its own memory — so it doesn't make things up.
Reranking
A second-pass model (a cross-encoder) that re-scores the retrieved chunks for true relevance to the question, so the best few reach the LLM. Retrieve top-20, rerank to top-5.
Hybrid search
Combining vector similarity with keyword full-text search, then fusing the rankings — catches exact-term matches that embeddings alone miss.
Faithfulness / groundedness
An eval metric: is every claim in the answer actually supported by a retrieved chunk? Often scored by an LLM-as-judge.
Multi-tenancy
Keeping each workspace's data separate and private. Your auth + policies already do this — RAG must respect it by filtering on workspace_id before similarity search.
Vector database
A database built to store vectors and find nearest ones fast (e.g. pgvector, Qdrant). You start with plain Postgres and upgrade to pgvector on the same database later.
